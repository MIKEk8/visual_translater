# Project Audit - Screen Translator v3.0 (Rust + Tauri)

## Findings

1. **Front-end invokes a missing backend command**
   - `processImageTranslation` calls `smart_translate_with_context` via Tauri `invoke`, but the Rust command registry in `src-tauri/main.rs` does not expose such a command and `src-tauri/commands/mod.rs` does not implement it. Any OCR-driven translation request will throw at runtime when the command is not found.

2. **OCR and screenshot pipeline is stubbed yet wired as if available**
   - Front-end quick-translation flows call `capture_screenshot` and `perform_ocr` expecting data-rich responses (`{ imageData }` and OCR text), but the backend implementations currently return errors and a plain `String` result. User-triggered screenshot or image translations will consistently fail until the commands are implemented and their response shapes align.

3. **Hotkey threshold argument name mismatch**
   - The front-end sends `thresholdMs` to the `update_quick_press_threshold` command, while the Rust handler expects `threshold_ms`. Tauri argument names are case-sensitive, so updates to the quick-press threshold will be rejected with a deserialization error.

## Recommendations

- Add a Tauri command (and handler wiring) for smart, context-aware translation or adjust the front-end to use the existing `translate_text` API until the smarter path is available.
- Implement `capture_screenshot` and `perform_ocr` to return structured objects that match the front-end expectations, or gate the UI to avoid invoking unimplemented features.
- Align the parameter naming between the hotkey hook and Rust command (e.g., send `threshold_ms` or rename the Rust parameter) to ensure hotkey tuning works.
- Introduce a thin service layer in the backend to isolate side-effects (screenshot capture, OCR calls, translation providers) from Tauri command handlers. This separation will simplify swapping providers (e.g., different OCR engines) and make unit testing easier by mocking service traits.
- Define shared DTOs/types for command payloads and responses that are consumed by both the React front-end and the Rust backend (e.g., via a small JSON schema or TypeScript/Rust codegen). This reduces drift in field names such as `thresholdMs` vs `threshold_ms` and prevents runtime deserialization errors.
- Add end-to-end smoke tests that exercise the UI-to-command boundaries: start the Tauri app, trigger screenshot → OCR → translate flows, and assert that structured data is exchanged. These can run in CI using a headless display (e.g., xvfb) to catch regressions in command wiring early.
- Create contract tests for each Tauri command using the `tauri::test` harness or integration tests in Rust that invoke commands with representative payloads. Assert error shapes and success schemas to ensure the backend remains compatible with front-end expectations.
- Gate unreleased features behind feature flags (e.g., `OCR_ENABLED`, `SMART_TRANSLATE_ENABLED`) surfaced in both front-end and backend. This allows shipping partial functionality without breaking flows when certain providers are unavailable.
- Document and standardize error shapes (codes + messages) so the front-end can handle failures gracefully (e.g., distinguish "provider unavailable" from "bad input"). Consider mapping external provider errors to a small, typed error enum exported to the UI.
